# Crossly business entity identifier standard

Status: implemented foundation. This standard applies to the website, versioned APIs, future Flutter apps, printed labels, QR codes, and barcodes.

## Two-layer identity

Every core record has two identifiers:

1. An immutable UUID primary key used internally by the database and APIs.
2. An immutable, typed Crossly code used by people, operations, labels, and support.

| Entity | Crossly code | External standard kept separate |
| --- | --- | --- |
| Natural person/account (customer, employee, administrator, or seller user) | `PER-…` | Government/KYC identifiers are private and never used as public IDs |
| Seller store | `STR-…` | GS1 GLN may be added after registration |
| Product | `PRD-…` | Supplier SKU and GS1 GTIN remain separate |
| Order | `ORD-…` | Marketplace/provider order number remains separate |
| Warehouse | `WHS-…` | GS1 GLN may be added after registration |
| Package | `PKG-…` | GS1 SSCC may be added for logistic units |
| Shipment | `SHP-…` | Carrier tracking number and optional GS1 GSIN remain separate |

A user receives one `PER` code even if the same account has multiple roles. Role changes must never create a second person identity.

## Required rules

- Codes are generated by the server/database, are globally unique, contain no personal information, never change, and are never reused.
- Clients cannot choose or overwrite a code. API payloads may return codes but mutation schemas must reject attempts to set them.
- A QR code or barcode encodes an identifier only. Possessing or scanning it never grants access; every API request still enforces authentication, role, assignment, and object ownership.
- Crossly codes are not carrier tracking numbers, supplier SKUs, or GS1 identifiers. Store each identifier in its own field.
- Customer/person codes are private to the owner and authorized staff. Store and product codes may appear publicly. Warehouse and shipment codes appear only where operationally relevant.
- Human-facing search should accept the typed code. Database relations continue to use UUID foreign keys.
- Audit logs record the actor UUID and affected entity UUID; the human-facing code may also be copied into metadata for investigation.

## QR, barcode, and GS1 rollout

Crossly may generate Code 128 and QR labels from its typed codes for internal operations. Global retail or logistics identifiers must not be invented. The owner must obtain the appropriate GS1 Company Prefix/identifiers and define allocation rules before Crossly publishes GTIN, GLN, SSCC, GSIN, or GINC values.

Recommended scanning payload: a short HTTPS URL or a versioned payload such as `crossly:v1:SHP-…`. The server resolves the code only after authorization and records the scan event. Never put customer name, phone, address, tokens, or secrets in the symbol.

## UUID evolution

The current UUID primary keys remain valid and secure. UUIDv7 can improve time-local insertion at very high write volume, but changing primary-key generation is a separate benchmarked migration—not a requirement for launch and not something to retrofit casually. Public Crossly codes intentionally do not reveal creation time.

## Implemented database guarantees

Migration `20260829090000_business_entity_codes` adds and backfills required unique codes for people, stores, products, warehouses, and shipments. Orders and packages already had typed unique codes. PostgreSQL defaults protect records created outside the application, and exact-format checks protect the new operational code families.

## Implemented operational surfaces

- A signed-in account receives its own `personCode` through `GET /api/v1/users/me`; authorized Admin customer APIs can search and return that same code. Public APIs never expose person/employee codes.
- Approved public stores expose and can be searched by `storeCode`. The Seller store API returns the seller's immutable store code separately from the editable business name and permanent slug.
- Shipment creation returns `shipmentCode` separately from carrier `trackingNumber`. Assigned Logistics staff can scan either value, package codes, or order codes; row-level warehouse assignment still controls resolution and every mutation remains audited.
- Logistics station views expose assigned `warehouseCode` values. Warehouse creation returns its generated code without accepting a client-supplied replacement.
- Public store product responses include each Crossly `productCode` separately from seller and manufacturer identifiers.
